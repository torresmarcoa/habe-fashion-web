# Habe Fashion Web — Agent Instructions

## Project Overview

Habe Fashion Web is a fashion portfolio website for a fashion designer.

The initial MVP is a public portfolio, not an e-commerce platform.

The repository is a public GitHub monorepo containing separate frontend and future backend applications.

## Required Context

Read these in order, and stop as soon as you have what the task needs:

1. `specs/product.md` — product vision, MVP scope, and open product decisions.
2. `specs/requirements.md` — numbered requirements (`REQ-<AREA>-<NNN>`) and acceptance criteria.
3. `docs/adr/` — the ADRs relevant to the area you are touching. Check the filename before assuming a decision; `specs/architecture.md` §16 lists them.
4. `docs/engineering-rules.md` — constraints that apply to every change.

Read `specs/architecture.md` only when the task touches technical structure, constraints, or an open decision.

For architectural changes, read the full decision context of the affected ADR, including its consequences and constraints.

If these documents conflict, do not silently choose whichever instruction is more convenient. Report the conflict and request a decision.

## Agent Skills

Installed skills live in `.agents/skills/`:

- `frontend-design` — guidance for visual design decisions. Use when building new UI.
- `vercel-react-best-practices` — React and Next.js performance rules. Use when writing or reviewing components.
- `brand-design` — Habe brand tokens and contrast rules. Use whenever colors or brand styling are involved.

### Rules Precedence

Skills are **advice**. This file, `docs/engineering-rules.md`, and the accepted ADRs are **binding**.

When a skill conflicts with a project rule, the project rule wins and the conflict is reported rather than silently resolved in either direction. Specifically:

- A skill never authorizes a dependency, framework, architectural pattern, or scope expansion that `docs/engineering-rules.md` §3 and §4 forbid. Read their rationale before applying a skill recommendation that would introduce infrastructure.
- A skill never overrides an accepted ADR or a documented open decision.
- Generic design advice from `frontend-design` never overrides the confirmed brand values in `brand-design` or the brand facts in `specs/product.md` §14.1.

Some skill recommendations align with these rules and are worth following: avoiding unnecessary client components and dead weight in the bundle (REQ-PERF-001), semantic HTML, and visible focus states (REQ-A11Y-002).

Note that `.agents/skills/*/AGENTS.md` and `.agents/skills/*/README.md` belong to upstream skills, not to this project. They are untracked and regenerated by the skills CLI. Do not treat them as project instructions.

## Project Constraints

- Frontend: Next.js, React, TypeScript, and Tailwind CSS.
- Backend: Node.js, Express, and TypeScript are the proposed future stack.
- Media provider: Cloudinary.
- Planned relational database: PostgreSQL; database access tooling remains undecided.
- The MVP must work without a custom backend.
- Hosting and deployment providers remain undecided.
- E-commerce is outside the MVP scope.
- The repository is public. Never commit secrets or private credentials.

Do not interpret a proposed technology or an unresolved decision as an approved implementation requirement.

## Working Procedure

For each task:

1. Identify the requirement and acceptance criteria.
2. Inspect the existing code and project conventions.
3. Identify assumptions, dependencies, and unresolved decisions.
4. Propose a plan for substantial changes.
5. Implement the smallest complete solution.
6. Run the applicable verification commands.
7. Review the final diff for unintended changes.
8. Report the changes, verification results, and remaining issues.

For small, unambiguous tasks, the plan may be brief.

## Verification Rules

- Discover the actual scripts available in the affected application before running checks.
- Do not invent commands or claim checks were successful without executing them.
- Report failed or unavailable checks explicitly.
- Do not suppress a failure simply to report completion.
- Do not claim that a feature is complete if its acceptance criteria remain unmet.

## Permission Boundaries

- Do not deploy or publish changes unless explicitly authorized.
- Do not perform destructive operations without approval.
- Do not discard or overwrite unrelated user changes.
- Do not introduce dependencies or change architecture without justification.
- Never expose secrets or private client information.

## Final Report

At the end of a task, report:

- What changed.
- Which requirement the change addresses.
- Which checks were executed and their actual results.
- Any checks that remain outstanding.
- Any unresolved decisions or follow-up work.
